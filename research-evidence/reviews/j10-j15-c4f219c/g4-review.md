## G4-J15-01 — P2: invalid saved taste-category recovery does not specify the resulting personalisation state

- **Classification:** missing visible contract for a known lifecycle risk, not an observed runtime loss or inferred security failure. It adds no capability or new preference input.
- **Path:** J15-A06 -> J15-P02/J15-P03 when a saved category is renamed, removed or replaced while the diner has confirmed preferences and a current publication changes.
- **Verified evidence:** line 309 says deleted/renamed categories are flagged for review and not matched to unrelated replacements. Line 311 distinguishes confirmed saved preferences from unsaved/uncertain changes. Line 316 intentionally matches all diet-eligible candidates in venue order when no taste categories are selected, while line 322 forbids silently weakening a diet constraint. Neither defines whether an invalid last saved taste selection remains a labelled orphan, suspends affected matching, becomes no-match, or is treated as an intentionally empty selection. Q17 line 496 names a renamed category but describes operation-revision/reset safeguards without the category-change recovery result. ADR-0010 line 41 records category lifecycle as a proposed design contract; it does not supply this result. Minimal CP-S04/B04 references preserve operator placement/source identity, not the diner's saved-category lifecycle.
- **Applicable expectations:** source J15.3/J15.4 and R17 require deliberate reviewable inputs and current contextual recommendations. No food-safety guarantee is involved; the gap concerns the meaning of saved preferences and predictable recovery.
- **Reproduction, explicitly fictional:** A saves C2 Vinos as the only taste category. Use Sin preferencia first, then separately a conditional declared-diet branch whose source attributes are awaiting the documented authorised intake (no real classification is claimed). A is online and authorised. A new publication removes Vinos or replaces it with another category identity while a recommendation request is pending. Separately contrast renaming the same category identity to Carta de vinos without changing its content meaning. Follow A06/P02/P03 after current-publication reconciliation.
- **Expected:** recognise that loss of the saved category is different from A deliberately choosing no tastes. Show the saved reference and its changed/unavailable status, a defined effect on affected recommendations and a concrete route to review the choice. Do not silently substitute a new category or reinterpret removal of the last selected category as diet-only personalisation. A same-identity rename has an explicitly chosen continuation/notice; replacement/retirement cannot adopt the old selection merely because names resemble each other. Public menu and legitimate current diet constraints remain available.
- **Actually described:** the review flag/no-unrelated-replacement invariant is useful, but its composition, next action and current-result consequence are absent. The no-category diet-only matching branch is concrete while the invalid-last-category branch is not. A reader must add assumptions to decide whether personalisation continues, falls back or requires reconfirmation. The document does not expressly instruct deletion or broadening; those are risks to exclude, not claimed executed faults.
- **Proposed correction:** preserve an invalid saved category as a visible unavailable reference. Use copy such as "Una categoría de tus preferencias ya no está disponible. Revisa qué quieres elegir" and Cambiar preferencias -> J15-A06. Pending review, suspend the affected personalised matching or show a specifically labelled no-match/fallback; do not silently drop the category and invoke the voluntary no-tastes rule. Define what happens with other still-valid saved tastes without fabricating replacements. A deliberate edit/reset/save then follows existing confirmed-result/conflict/permission rules. Define separately a rename that retains the same meaningful category identity; G3 specifies identity/deletion mechanics in #4.
- **Recheck criteria:** read (1) rename with stable identity; (2) retirement of the only saved category with diet selected; (3) retirement with another valid taste remaining; (4) similar-name replacement with a new identity; (5) an old recommendation response arriving after retirement; (6) user explicitly removes the unavailable reference and confirms diet-only/no-tastes inputs. Each must identify source/preference revision, visible reason, allowed candidate behavior and exact destination. Retained inputs must not migrate across user/venue or weaken diet; unsaved/unknown changes cannot become confirmed recommendations. No actual source or backend is required to write these contrasts.
- **Owner/checkpoint:** G2 supplies the visible states, G1 consolidates the routine operational behavior, G3 defines identity/storage/enforcement in M2. Required before the affected category-change J15 design branch is claimed resolved. No repeat founder scope approval is needed.
